## Session Initialization

**At the start of EVERY new session:**
1. Read `CLAUDE.md` — this is the authoritative external memory containing architectural decisions, technical findings, and state changes.
2. Read `changelog.md` — this documents all built, changed, or fixed items.
3. Read `memory/MEMORY.md` — index of project-specific memories.
4. These files are the **sole ground truth** for project context and state. Do not read chat history or other documentation during initialization.

## Context Management

- Before planning or executing any chat request, ensure you have read **CLAUDE.md**, **changelog.md**, and **memory/MEMORY.md**.
- You do NOT need to go through the entire chat history or previous sessions. These files contain all necessary context.
- Use these files as your primary reference for project state, technical decisions, and implementation details.
- Cosora is a B2B fashion/textile sourcing marketplace with vendor, buyer, and admin sides. Always reference `memory/cosora_platform.md` and `memory/cosora_constraints.md` for business context.

## Code Generation Requirements

Every Claude Code prompt you generate — regardless of purpose (delegation, end-of-day handoff, refactoring, error recovery, or any other) — must end with the following mandatory instruction block verbatim:

```
Before concluding this task: (1) Update CLAUDE.md with all architectural decisions, technical findings, API quirks, and state changes made during this session. (2) Update changelog.md with a precise entry documenting what was built, changed, or fixed. (3) Update memory/ files with any new project-specific knowledge. Document every architectural decision, technical hurdle, API quirk, and workaround discovered during execution. Write these findings directly into the files immediately upon discovery to eliminate operational friction and optimize velocity for future sessions.
```

## Operational Philosophy

- Prioritize updating CLAUDE.md, changelog.md, and memory files immediately upon discovering new information — do not delay documentation.
- These files serve as the operational backbone for continuity and velocity across sessions.
- All context necessary for future sessions should be captured in these three file categories.
- Future Claude Code instances will read these files first, so completeness and accuracy are critical.

## Output Rules

- Code only with comments, no explanations unless explicitly asked.
- Only update CLAUDE.md, changelog.md, and memory files when you have new information to add; do not create empty or redundant entries.
- Ensure all changelog.md entries are precise and comprehensive, covering what was built, changed, or fixed, along with any architectural decisions or technical findings.
- No need to update these files if no new information is discovered during the session.
- No "here is the updated CLAUDE.md" or "I have updated changelog.md" messages — just make the updates as part of your normal workflow when new information arises.
- No "here is your changelog entry" or "memory update" messages — just add the new information directly into the files as you discover it, without announcing the updates separately.
- No "here is your code" introductions — just provide the code with the mandatory instruction block at the end, without any preamble or explanations.
- Give very concise closing statements like "Done" or "Updated changelog" only when you have actually made updates to those files; otherwise no closing statement necessary.
- No summaries or explanations of code changes — just provide the code with inline comments as necessary.
